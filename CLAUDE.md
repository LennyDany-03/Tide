# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Tide — a Flutter habit-tracker prototype. The repo directory is `Loopify`, but the Dart package is `tide` (imports are `package:tide/...`) and the Android app id is `com.example.tide`. Flutter 3.44 / Dart SDK ^3.12.2. Dependencies: `go_router`, `supabase_flutter` (accounts, habits, realtime), `google_sign_in` (native picker → Supabase ID-token sign-in), `shared_preferences` (device flags, the habit cache and the write outbox). There is no state-management package.

## Commands

```bash
flutter pub get
flutter run --dart-define-from-file=.env   # -d chrome | windows | <device id>; VS Code passes the flag for you
flutter analyze                   # lints via flutter_lints (analysis_options.yaml)
flutter test
flutter test test/widget_test.dart
flutter test test/streak_calculator_test.dart --plain-name 'an unlogged today does not break the streak'
flutter test tool/email_assets_test.dart   # redraws supabase/email/tide-mark.png
```

`.env` (git-ignored; template in `.env.example`) holds `SUPABASE_URL`, `SUPABASE_PUBLISHABLE_KEY`, `GOOGLE_WEB_CLIENT_ID`, read as compile-time `String.fromEnvironment` in `lib/config/supabase_config.dart` — a changed `.env` needs a full restart. Without it the app falls back to in-memory accounts and habits. The database side is two scripts pasted into the Supabase SQL editor: `supabase/auth_setup.sql` (profiles table, RLS, triggers, `account_status` and `delete_account` RPCs, `email-assets` bucket), then `supabase/habits_setup.sql` (`habits` and `habit_entries` tables, RLS, the `habits_snapshot` RPC, and the triggers + `realtime.messages` policy that broadcast changes on the private topic `habits:<user id>`). The confirmation email and its dashboard settings are in `supabase/email/`.

## Architecture

**Habits sync through a repository; the store stays the source of truth.** `TideStore` (`lib/services/tide_store.dart`) is a `ChangeNotifier` holding every habit, preference and mutation. A mutation changes the list first (a log lands under the finger), then hands the touched rows to `HabitRepository` (`lib/services/habits/`) — `saveHabit`, `saveEntry(habit, day)`, `removeHabit`, plus `remember(list)` for the device copy. `SupabaseHabitRepository` puts every write in a `HabitOutbox` saved on the device before sending. Writes are whole-row upserts, never deltas, so a replay is harmless and a later write to a waiting row replaces it in place (which keeps a habit ahead of its entries for the foreign key). It reads the account with `habits_snapshot()` only once the outbox is empty, discarding the answer if a write happened meanwhile, and listens on the private realtime channel. Rows carry the writing process's `origin`, so a device's own echoes are skipped, and so is a remote change to a row with a local write still queued. Remote changes arrive as a `HabitChange` (`HabitsReplaced` / `HabitSaved` / `HabitRemoved` / `HabitEntrySaved`) and `_applyRemote` applies them without writing back or celebrating. An undone day is written as an empty entry (`amount` null, not frozen), never deleted. Log out flushes for a few seconds, then `close(forget: true)` drops the cache and outbox. `HabitRows` (`habit_rows.dart`) is the one codec for rows, the snapshot and the cache. `DemoHabitRepository` (tests, unconfigured runs) keeps lists in memory and answers `SeedData.habits()` for any account it holds nothing for. Preferences and the palette are still session-only. The signed-in account survives restarts (Supabase keeps the session until log-out), and `DeviceFlags` (`lib/services/device_flags.dart`) remembers that onboarding was seen, which accounts have had the tour, and the address of a sign-up waiting on its emailed code. Adding persistence means adding it in the store and repository, not in screens.

**Auth** (`lib/services/auth/`). `AuthService` is the seam: `SupabaseAuthService` for real builds, `DemoAuthService` (in memory, knows `jules@tide.app` / `tidewater`, accepts code `123456`) for tests and unconfigured runs. Both enforce the same rules — log in only reaches an existing, confirmed account; create only makes a new one — and throw `AuthFailure(AuthProblem…)`, which the screens turn into field errors or a notice offering the other mode. Supabase can't distinguish "no account" from "wrong password", so the service asks the `account_status` RPC (`none` / `unconfirmed` / `password` / `google`) after a refused login and before sign-up / Google. Google goes through `google_sign_in` + `signInWithIdToken` so the address is known *before* Supabase creates anything. **Email sign-up is confirmed by a 6-digit code, not a link**: `createAccount` returns `SignUpOutcome.needsCode`, the store records `pendingVerificationEmail`, and `VerifyEmailScreen` (`lib/screens/verify_email/`) calls `store.verifyEmailCode` (Supabase `verifyOTP`, type `signup`). Code length, lifetime and resend cooldown live in `AppConstants` and must match the Supabase Email provider settings and the template. The store's account actions never navigate on sign-in: an account "arrives" (profile read → new or returning, habit repository opened, tour armed, pending code cleared) and `store.sessionChanges` notifies the router. A new account opens empty with the tour; a returning one opens on this device's cached habits, replaced by the server snapshot when it lands. **Account deletion** is Settings → Danger zone: the row opens a `TideDialogPanel` (`lib/screens/settings/widgets/delete_account_dialog.dart`) whose `HoldToConfirmButton` calls `store.deleteAccount` → the `delete_account` RPC (security definer, deletes only `auth.uid()`, cascading identities, sessions, the profile and every habit — the service-role key never ships), then a local sign-out. Unlike log out it refuses offline and keeps the session. The store records `deletedAccountEmail` *before* the request (Supabase's sign-out event can beat the call's return), and while it is set the guard sends the signed-out app to `Routes.accountDeleted` (`AccountDeletedScreen`) instead of auth: the shared `TideTick` (`lib/widgets/tide_tick.dart`, also the code screen's tick) draws, and the screen waits on Done, which clears the flag and `go`es to auth.

**Store access.** `TideScope` (`InheritedNotifier`) is mounted in `main.dart` *above* the router so root-navigator sheets share it. Two accessors, and the difference matters:
- `context.tide` (extension on `BuildContext`, defined at the bottom of `tide_store.dart`) / `TideScope.of` — reads **and subscribes**; use in `build`.
- `TideScope.read(context)` — reads without subscribing; use in callbacks and one-shot actions.

**All arithmetic lives in `StreakCalculator`** (`lib/services/streak_calculator.dart`) — pure functions, no widgets or state. Streaks, completion rates, weekly series, weekday rates, heatmap intensities and clean streaks all resolve through it, so two screens can't disagree about the same figure. The store is a thin façade over it. New derived numbers belong here, not in a widget.

**Data model.** `Habit` (`lib/services/models/habit.dart`) is immutable; every mutation goes through `copyWith`, and the store mutates by rebuilding the list (`_mutate`). Ids are v4 UUIDs from `store.newHabitId()` — `habits.id` is a uuid the app chooses, so a habit made offline can have entries queued against it. Logs are `Map<DateTime, num>` keyed by `DateUtils.dateOnly` — always normalise dates to midnight before keying; on the server a day is a `date` column. `frozenDays` are days where a freeze token was spent so a miss doesn't break the loop. `HabitType` decides the logging gesture: `binary` → swipe, `quantity`/`duration` → hold-to-fill.

**Routing** (`lib/config/app_routes.dart`). go_router with a `StatefulShellRoute` of four branches (Today / History / Insights / Settings) rendered by `TideShell`. All four branches set `preload: true` — tabs are swipeable, so a lazily-built branch would appear blank under the finger. Milestones, the add/edit sheet and the upgrade sheet are pushed on the root navigator (`_rootKey`); the sheets are non-opaque `CustomTransitionPage`s so the screen behind stays visible. Use the `Routes` constants, never literal path strings. A top-level `_guard` redirect (refreshed by `store.sessionChanges`) owns who may be where: signed-in users at onboarding/auth go to `Routes.welcome` (first name, then Today); `Routes.verifyEmail` needs a pending sign-up, and stays put while signed in so its success tick can finish before it `go`es to the welcome itself; signed-out users anywhere in the app go to auth, or onboarding if this device has never seen it; onboarding is unreachable once seen on an earlier launch. `state.extra` carries `AuthDraft` (back to sign-up with the address kept) and `CodeDelivery` (whether Resend starts locked). A real launch starts on `Routes.splash` (`SplashScreen`, `lib/screens/splash/`), which plays the logo entrance and then `go`es to Today (restored session), the code screen (pending sign-up), auth, or onboarding; the native launch windows (Android `values*/styles.xml`, iOS `LaunchScreen.storyboard`, web `index.html`) are painted Midnight's ground so there is no flash either side of it. The tour overlay (`TourHost`, above the router) only shows while the current path is Today.

**Shell** (`lib/screens/shell/tide_shell.dart`). Owns the page ground, the tab bar and the FAB. `TideBackdrop` is mounted once here so all four tabs share one continuous background. Branch bodies stay alive in a stack. The FAB routes to `Routes.newHabit` or, when `store.canAddHabit` is false, to `Routes.upgrade` — the paywall is contextual, triggered by the free ceiling (`AppConstants.freeHabitLimit`), never a settings row. Pull to refresh on Today calls `store.sync()`, which flushes the outbox and re-reads the snapshot.

**Screen layout.** Each screen is `lib/screens/<name>/<name>_screen.dart` plus a private `widgets/` folder; anything used by more than one screen graduates to `lib/widgets/` (e.g. `AccountAvatar` — Google photo or initials — shared by Settings and the welcome). `Scaffold.extendBody` is true, so scrolling screens must pad the bottom with `TideTabBar.reservedHeight(context)` for the frosted bar to have something to blur.

## Design system — the constraints that actually bind

The theme layer is prescriptive, not advisory. Read the doc comments in `lib/theme/` before adding visual code.

- **`TideColors` is the entire colour vocabulary**, and its tokens are *getters* reading the active `TidePalette` (`lib/theme/tide_palette.dart`: Midnight — the default, `TidePalettes.standard` — plus Deep water, Ink, Blossom, Paper). No file outside `lib/theme/` may introduce a hue. The fix for a flat-looking screen is motion, depth and consistency — never a new colour. (The one exception is `supabase/email/confirm_signup.html`, which cannot read tokens and hard-codes Midnight's hex values.)
  - Because tokens are runtime values, never put them in a `const` expression or a default parameter value (make the parameter nullable and fall back inside `build`). `TideType` styles are getters for the same reason.
  - Ink on a solid accent fill is `TideColors.onLantern`, never `deepWater` — on light palettes the two differ.
  - Switch palettes only through `store.setPalette`, which calls `TideTheme.applyPalette` to rebuild and repaint the tree. A new palette must pass `test/palette_test.dart`'s contrast floors.
- **`TideGradients` holds every ramp**, all running top-left→bottom-right or top→bottom: one light source for the whole app. A gradient is depth, never decoration.
- **`TideMotion` holds every duration and curve.** Do not inline a `Duration` or `Curve` in a widget; add a named constant there so nine screens keep moving as one object.
- **`PressScale` is the only press affordance.** Material ink is disabled in `TideTheme` (transparent splash/highlight, `NoSplash`), so an unwrapped tappable feels dead. Destructive actions (and log out) use `HoldToConfirmButton` instead.
- **`TideSurface` / `TideWell`** carry the elevation recipe (fill, radius, shadow set, 1px top inner highlight). Don't hand-roll a `Container` card.
- **`GaugeNumber` / `GaugeCountUp`** render every number on screen, in JetBrains Mono with tabular figures. One glyph per column per frame — no two-drum odometer, no crossfade between digits; the motion is in the tweened *value*. `test/gauge_number_test.dart` enforces this.
- **`TideType`**: Space Grotesk for display/headings, Manrope for body/UI, JetBrains Mono for numerics. Text scaling is clamped to 0.9–1.2 in `main.dart` because the gauges are fixed-width.
- **Glyphs are abstract geometry** (`TideGlyph`, drawn by the painter in `lib/widgets/habit_glyph.dart`), never pictographic icons.
- **The logo is `TideLogoPainter`** (`lib/widgets/tide_logo.dart`): ring, tide, moon, orbiting point, animated through a `TideLogoFrame`. `TideMark`, the splash, the platform app icons and the email logo all draw from it. After changing it, regenerate the icons with `flutter test tool/brand_assets_test.dart` (kept out of `test/` because it writes into `android/`, `ios/` and `web/`) and the email logo with `flutter test tool/email_assets_test.dart`, then re-upload `tide-mark.png` to the `email-assets` bucket.

## Testing

`TideApp()` with no `auth`/`flags`/`habits` runs on `DemoAuthService`, `DeviceFlags.memory()` and `DemoHabitRepository`, so no test touches the network or disk. `TideApp(startOnboarded: true)` marks onboarding seen and signs the demo account in, booting straight into the shell on the seed history — that flag exists for tests and deep links; `TideApp(flags: DeviceFlags.memory(onboardingSeen: true))` opens on the account form, and adding `pendingVerification:` opens on the code screen. `showSplash` is off by default (only `main()` turns it on), so tests start where they ask to; `test/splash_test.dart` is the one place it is on. Use fixed `tester.pump(Duration(...))` rather than `pumpAndSettle`: several screens run deliberate ambient loops (breathing empty state, sync pulse, CTA glow, onboarding drift, the envelope's orbiting point) that never settle. Shared helpers (`settle`, `pumpFor`, `pressAuthButton`, `enterEmailCode`, `crossWelcome`) live in `test/support/flow.dart`; the code screen's tick and the welcome both chain animation → timer → route, so cross them with `pumpFor`'s small steps, not one long pump. Time-dependent logic tests pass an explicit `asOf` so they don't drift with the wall clock (see `test/streak_calculator_test.dart`). Sync is tested without Supabase: `test/habit_sync_test.dart` drives the store through a recording fake repository that can also announce remote changes, and `test/habit_outbox_test.dart` / `test/habit_rows_test.dart` cover the queue and the codec. `test/failures/` holds checked-in golden diff PNGs, not test code.

## Conventions

- Config-as-data lives in `lib/config/`: `AppConstants` (limits, copy, the tab manifest, email-code length/lifetime/cooldown), `HabitTemplate.all`, `MilestoneCatalog`, `SeedData`, `SupabaseConfig`. Tune numbers there rather than in screens.
- Seed data is real log history, not hardcoded display strings — its patterns are tuned so the computed figures land on the design's numbers (12-day water streak, ~82% week, four milestones unlocked). It is demo-only now: real accounts never see it, but the demo account and the tests do, so changing it changes what those report.
- A new habit column means changing `supabase/habits_setup.sql`, `HabitRows.habit` and `HabitRows.parseHabit` together; parsing stays forgiving (unknown glyph → `TideGlyph.dot`) so rows from a newer build still open.
- Prefer `abstract final class` for the token/constant holders, matching the existing files.
- Comments in this codebase explain *why* a non-obvious choice was made (why branches preload, why no odometer, why the radial falloff has seven stops). Match that when touching those areas.
- Only public values go in `.env` / the app (Supabase publishable key, Google client IDs). The Supabase secret/`service_role` key and the Google client secret belong only in the Supabase dashboard. The confirmation email shows no user-supplied data (no name): anyone can sign up with anyone's address.
